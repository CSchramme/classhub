# Database

PostgreSQL via Prisma 7 (`prisma-client` generator, output at `generated/prisma`,
not committed — regenerated by `npm run db:generate` / the `postinstall` hook).
Prisma 7's client requires an explicit driver adapter; we use `@prisma/adapter-pg`
(`pg` under the hood) — see `lib/db.ts` for the singleton and `prisma7.config.ts`
for CLI/migration config (Prisma 7 no longer auto-loads `.env` for CLI commands,
hence the `dotenv/config` import there).

Full model definitions live in [`prisma/schema.prisma`](../prisma/schema.prisma).
This doc covers the decisions that aren't obvious from reading it.

## Partial unique indexes (hand-added, not in schema.prisma)

Prisma's schema language has no syntax for a partial (`WHERE ...`) unique
index, so two correctness-critical invariants are added by hand-editing the
generated migration SQL rather than declared in `schema.prisma`:

1. **Exactly one `SYSTEM_ADMIN` ever** (spec §6):
   `CREATE UNIQUE INDEX "User_one_system_admin" ON "User" ("role") WHERE "role" = 'SYSTEM_ADMIN'`.
   Registration logic checks whether any user exists to decide the intended
   role, then attempts the insert; if a concurrent request already won the
   race, this index turns the loser's insert attempt into a unique-constraint
   violation, which the app catches and retries as `STUDENT` instead. This
   makes the invariant a real database guarantee, not just an application-level
   check that a race could slip past.

2. **At most one active membership per (user, class)** (spec §17):
   `CREATE UNIQUE INDEX "ClassMembership_one_active_per_user_class" ON "ClassMembership" ("userId", "classId") WHERE "leftAt" IS NULL`.
   `leftAt` is nullable rather than hard-deleting the row so membership
   history and future re-joins are preserved; the partial index still
   prevents two simultaneously-active memberships in the same class.

Any future migration that touches these tables must preserve both indexes —
`prisma migrate dev` won't regenerate them since they're invisible to the
schema.

## File / Folder ownership

A `File` or `Folder` is owned by exactly one of `ownerUserId` (private cloud)
or `ownerClassId` (class cloud). This is enforced in `lib/storage` (Phase 12/13),
the only code path allowed to write these tables — not by a database check
constraint. Given the server-action architecture (spec §71/72), nothing else
ever writes to these tables directly, so the app-layer invariant is
sufficient without fighting Prisma's limited constraint support for this.

## Storage quotas

`User.storageUsedBytes` / `Class.storageUsedBytes` are denormalized counters,
not computed on demand from `SUM(File.sizeBytes)`. They're updated with a
single atomic conditional update —
`UPDATE ... SET used = used + $size WHERE used + $size <= $quota`
— in the same transaction as the `File` insert. This is what actually closes
the parallel-upload race from spec §33 (test #12): a `SUM`-then-insert
approach has a race window between reading current usage and writing the new
file that two concurrent uploads can both pass through; a single
conditional `UPDATE` cannot.

## `Class.slug` is globally unique

The fixed route is `/klasse/[classSlug]` with no school or year segment
(spec §4), so slugs can't be scoped per school. Class creation (Phase 5)
needs to generate/validate a globally-unique slug (e.g. suggest a suffix on
collision) rather than just deriving one from the name.

## `SystemSettings` singleton

One row, `id = "singleton"`, holds `aiGloballyEnabled` (spec §35). This has
to be a database row rather than an env var because the admin UI toggles it
at runtime (spec §51) — env vars would need a redeploy. It's a convention,
not a DB-enforced singleton: the app always reads/writes `id = "singleton"`
via upsert, and nothing else writes this table.

## `Invitation` (spec §13) folded into `SetupToken`

The spec's entity list names both `Invitation` and a setup-link flow, but
the concrete mechanism described (spec §8) is one thing: an admin creates the
`User` row directly with `PENDING_SETUP` status and a token is issued for
that existing user to set their own password. There's no separate
"invited but no account yet" state in V1. Modeling both would mean one of
them stays empty and unused, so `SetupToken` alone covers it. Revisit if a
future phase adds a real pre-account invite flow (e.g. emailing a
prospective Teacher/Parent before they have a `User` row).

## Why `Homework` covers both personal and class homework

`Homework.classId` is nullable: `null` means private to the author (spec
§19, `/home/hausaufgaben`); set means shared with the whole class (spec §28,
`/klasse/[slug]/aufgaben`). One model instead of two avoids duplicating
almost-identical fields and lets a class's shared homework and a student's
own homework list share the same query/filtering code.
